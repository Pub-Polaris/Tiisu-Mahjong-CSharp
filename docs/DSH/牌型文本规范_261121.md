# 牌型文本规范 v1

日期：2026-11-21

## 目的

统一人类可读牌型、机器规范化牌型、语义化副露显示三件事的写法。

JS 时代的问题是：把“文本里的分组”误当成“牌型结构”。
这里明确：**数字串只表示牌的多重集（multiset）；分组、空格、分隔符只影响阅读，不影响牌型。**

## 1. 手牌 compact 写法

```text
<数字串><花色>
```

花色：

```text
m = 万
p = 筒
s = 索
z = 字
```

一个花色字母作用于它前面、上一个花色字母之后的**全部数字**。

```text
112233m
= 11m 22m 33m
= 1m 1m 2m 2m 3m 3m
```

等价示例：

```text
11223344556677z
== 11z22z33z44z55z66z77z

112233m445566p556677z
== 11m22m33m44p55p66p55z66z77z

123456789m
== 123m456m789m

111222333444p
== 111p222p333p444p

123999p234s
== 123p999p234s
```

## 2. canonical 形式

- 花色顺序：`m → p → s → z`
- 每种花色内数字升序
- 数字连续写，不保留无意义空格
- 13/14 张由调用方校验，不由语法层强绑

```text
123m456m789m -> 123456789m
11m22m33m    -> 112233m
```

## 3. 分隔符

允许：

```text
空格   /   |   -   _
```

解析时全部忽略。

```text
112233m 445566p 556677z
112233m/445566p/556677z
112233m|445566p|556677z
```

三者都等价。

## 4. 校验

- 只允许数字 `1..9`
- 字牌只允许 `1..7`
- 每种牌最多 4 张
- 不能出现未知花色
- 空段、空数字串非法
- `123m456p789` 非法：末尾没有花色

## 5. 唯一的结构边界：`123333p`

`123333p` 是：

```text
1p + 2p + 3p + 3p + 3p + 3p
```

共 6 张。

它**可以**被人类理解成：

```text
12p + 3333p
```

也可以被理解成：

```text
123p + 333p
```

但这两种都是**结构解释**，不是文本本身的含义。

因此：

- 牌型文本只保存 multiset
- 不把 `123333p` 强行解释成某一种拆法
- 真正的面子/对子拆分由判和、听牌、赋数算法决定
- 人类要表达明确拆法时，用分隔符或副露 token，而不是靠紧凑数字串

代码里必须只解析成计数，不得在解析阶段猜 `12p + 3333p` 或 `123p + 333p`。

## 6. 副露 token

推荐前缀：

```text
c = 吃（chi）
b = 碰（pon）
a = 暗杠（ankan）
k = 明杠（minkan）
```

使用 `b` 而不是 `p`，避免与筒子花色 `p` 混淆。

示例：

```text
c123m   吃 123 万
b777z   碰 7 字
a222z   暗杠 2 字
k333p   明杠 3 筒
```

### 花色省略

下面的短形式只有在**外部上下文已经给出花色**时才成立：

```text
c123
k333
```

单独作为字符串时，它们不是自足语法：

- `c123` 不知道是万、筒还是索
- `k333` 不知道是万、筒还是索

所以：

- canonical 副露 token 必须带花色：`c123m`、`k333p`
- 短形式只能用于“牌桌显示”，不能作为解析器的唯一输入
- 解析器遇到缺花色的 `c123` / `k333` 必须报错或要求 context，不能猜

`b777z`、`a222z` 带 `z`，没有这个问题。

## 7. 未来用途

这套 token 以后用于：

- 游戏内语义化牌型提示
- 指南、牌例、测试数据
- 牌谱紧凑展示
- 和牌/副露说明

显示层可以输出人类友好的分组；解析层只保留 multiset 和明确副露 token。
